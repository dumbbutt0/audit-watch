## Checks to perform (in priority order)

### 1. First-depositor inflation attack
The canonical ERC-4626 exploit: when `totalSupply == 0`, an attacker deposits 1 wei to
receive 1 share, then donates a large amount of assets directly to the vault, inflating
the share price. The next depositor receives 0 shares (rounded down) while their assets
are stolen.

Check for:
- Does `convertToShares` use `mulDiv(assets, totalSupply, totalAssets)` with no virtual
  offset? If `totalSupply` and `totalAssets` can both be 1 and a large donation is possible,
  inflation is live.
- **Mitigation check:** Does the vault implement a virtual shares/assets offset?
  - OZ v5 style: `_decimalsOffset()` returning ≥ 3 adds virtual 10^offset shares + assets
  - Manual style: `totalSupply + VIRTUAL_SHARES` and `totalAssets + VIRTUAL_ASSETS` in the
    conversion formula
  - If no offset: flag as High/Critical depending on donation feasibility

### 2. Donation attack via direct token transfer
Even with virtual shares, if `totalAssets()` reads `token.balanceOf(address(this))` (spot
balance), an attacker can donate tokens to inflate `totalAssets` and dilute existing holders.

Check:
- Does `totalAssets()` use `token.balanceOf(address(this))` or an internal accounting variable?
- If spot balance: is there a mechanism to prevent or absorb donations (e.g., a sweep
  function, a minimum deposit, or a `lastTotalAssets` tracker)?
- If internal variable: is it updated correctly in every deposit/withdraw/transfer path?

### 3. Rounding direction violations
ERC-4626 mandates specific rounding directions to protect the vault:
- `deposit(assets)` → `convertToShares` must round DOWN (user gets fewer shares)
- `mint(shares)` → `convertToAssets` must round UP (user pays more assets)
- `withdraw(assets)` → `convertToShares` must round UP (user burns more shares)
- `redeem(shares)` → `convertToAssets` must round DOWN (user receives fewer assets)

Check each conversion call for `Math.mulDiv` rounding mode:
- `Math.mulDiv(a, b, c, Math.Rounding.Floor)` → rounds down
- `Math.mulDiv(a, b, c, Math.Rounding.Ceil)` → rounds up
- A plain `a * b / c` always rounds down — this is wrong for mint and withdraw

Any violation of the rounding rules means the user can extract more value than they deposit.

### 4. totalAssets() flash loan manipulation
If `totalAssets()` reads a spot balance and the vault interacts with a DeFi protocol
(e.g., Aave, Compound, Yearn) that can be manipulated intra-transaction:

Check:
- Can an attacker use a flash loan to inflate `totalAssets()` before a deposit, causing
  the depositor to receive fewer shares than fair?
- Can an attacker deflate `totalAssets()` before a redemption, causing the redeemer to
  receive fewer assets than fair?
- If `totalAssets` reads from a protocol whose liquidity can be manipulated (e.g., a pool
  with low TVL), flag as Medium or High depending on liquidity depth.

### 5. Reentrancy on deposit/withdraw via ERC-777 underlying
If the underlying token implements ERC-777 `tokensToSend` or `tokensReceived` hooks,
a malicious recipient contract can reenter the vault during a transfer:

Check:
- Does `deposit` transfer tokens from the user BEFORE minting shares? (CEI violation)
- Does `withdraw` burn shares AFTER transferring assets? (CEI violation)
- Is there a `nonReentrant` guard on both `deposit` and `withdraw`?
- Even with `nonReentrant`, cross-function reentrancy is possible if the guard is per-function:
  attacker reenters a different function (e.g., `transfer` shares) during the hook.

### 6. maxDeposit/maxMint/maxWithdraw/maxRedeem accuracy
ERC-4626 requires these to return the maximum amount that would succeed in the corresponding
operation. Returning `type(uint256).max` when the vault is paused or has a deposit cap
violates the spec and misleads integrators:

Check:
- Do these functions return 0 when the vault is paused?
- Do they respect any configured deposit caps or per-user limits?
- Is `maxWithdraw` accurate when the underlying assets are partially illiquid (locked in
  a strategy)?

### 7. previewDeposit / previewRedeem accuracy
The preview functions must return the same result as the actual operation (within rounding):
- If `previewDeposit(100)` returns 99 but `deposit(100)` mints 98 shares, integrators
  building on top will miscalculate and expose users to losses.
- If fees are deducted in `deposit` but not in `previewDeposit`, the preview is wrong.

Check every place where fees, slippage, or off-by-one rounding could make preview
diverge from actual by more than 1 wei.

### 8. Fee-on-transfer underlying asset
If the underlying token deducts a fee on transfer:
- `deposit(assets)` transfers `assets` but the vault receives `assets - fee`.
- If the vault does not account for this, it credits the depositor with more shares than
  the received assets justify.
- Check if `totalAssets` is updated using `balanceOf` (which auto-accounts) vs a delta
  check (`received = balanceAfter - balanceBefore`).

### 9. ERC-4626 compliance with yield-bearing upgrades
If the vault upgrades the underlying strategy mid-flight (e.g., migrates from Aave v2 to v3):
- Check that `totalAssets` is updated to reflect the new strategy's balance.
- Check that the share price does not jump or drop at migration time.
- Check that pending withdrawals can still be fulfilled after migration.

## max*/limit fidelity — the limit must match the action it bounds
> Recall-widening class (P303, generalized from blind-eval misses). Advisory pre-flags in
> `output/erc4626_limit_fidelity_audit.json` (research-only).

A `max{Deposit,Mint,Withdraw,Redeem}`/limit MUST be faithful to the action it bounds, or the advertised max
reverts or over-reports (breaking the ERC4626 invariant that an action of `max*` succeeds). Check:
- **Primitive parity:** the limit and its action must use the SAME underlying primitive
  (`maxDeposit↔deposit`, `maxMint↔mint`, `maxWithdraw↔withdraw`, `maxRedeem↔redeem`). Flag when e.g. `maxDeposit()`
  bounds via `underlying.maxDeposit()` but the deposit path calls `underlying.mint()` — the cap is computed against
  a primitive the action never uses, so depositing the reported max can revert.
- **Cross-basis estimates:** a max-withdraw/redeem bounded via `convertToAssets(maxRedeem(...))` /
  `convertToShares(maxWithdraw(...))` is an asset↔share estimate that need not match the action's redemption
  rounding — the reported max can over-report and revert at the boundary.
- **Cap omits accrued claimable:** a deposit/mint cap computed from a base supply (e.g. `type(uint96).max -
  totalSupply`) must also subtract any separately-accrued mintable balance (fee/reward shares, e.g.
  `yieldFeeBalance`) that consumes the same cap; otherwise the cap over-reports.

KB crossref: `search_findings(vuln_type="logic-error", query="ERC4626 maxDeposit maxWithdraw limit mismatch deposit mint redeem over-report")`.
Severity: usually Medium (deposit/withdraw DoS at the limit, or an unfulfillable max breaking integrators).

## Common false positives to exclude
- Vaults using OZ v5 ERC4626 with non-zero `_decimalsOffset()` — inflation is mitigated
- `totalAssets()` using an internal accounting variable, not spot balance — donation attacks don't apply
- Rounding in `convertToShares` that rounds down but is only called from `deposit`
  (correct direction) — check the call site, not just the function
- Protocols with a minimum deposit that prevents 1-wei first deposits

### Meta-vault (ERC4626-of-ERC4626) deposit/withdraw lacks slippage + deadline protection (p321, silo M-4)
A meta-vault whose share price moves with underlying-market interest accrual AND permissionless reallocation MUST expose min-shares/min-assets + deadline on deposit/mint/withdraw/redeem — the standard ERC4626 4-arg signatures (deposit(assets,receiver) / withdraw(assets,receiver,owner)) are insufficient: an attacker can sandwich a reallocation or interest jump to give the user a worse share price, and a stale tx can execute much later. Absence-gate: confirm NO minShares/minAssets/deadline param exists across ALL four entrypoints (silo: SiloVault.sol:569/586/603/625 — all bare 4626). Recommend wrapper functions with bounds. Distinct from AMM-swap slippage: here the manipulable variable is the vault share price via market interest/reallocation.

### Meta-vault supply loop omits underlying market maxDeposit while the view counts it (p321, silo M-6)
Asymmetry bug: `maxDeposit()`/`_maxDeposit()` bounds suppliable by `min(config.cap - balance, market.maxDeposit(this))` (silo SiloVault.sol:683), but the actual allocation loop `_supplyERC4626` computes `toSupply = min(config.cap - supplyAssets, assets)` with NO `market.maxDeposit` term (SiloVault.sol:879) and wraps the deposit in try/catch. So when a market is full at its ERC4626 maxDeposit but has config-cap room, `market.deposit(toSupply)` reverts and the WHOLE market is skipped — deposits the view advertised as feasible fail (AllCapsReached) or get misrouted. RULE: any allocation loop must cap each leg by the SAME bounds its capacity view advertises (config cap AND live maxDeposit), and should deposit the fittable portion rather than all-or-nothing. Verify by diffing the view's bound set vs the loop's bound set.

### One-directional (up-only) position tracker ignores rounding-down losses -> backing over-stated, deflation over cycles (p321, silo M-1/M-06)
When a vault tracks its position in an underlying market with a cached balance that is only ratcheted UPWARD (high-water mark), per-operation rounding losses are never deducted, so accounted backing drifts ABOVE true redeemable. Silo: `balanceTracker[market] += suppliedAssets` records ASSETS deposited (not the rounded-down shares actually minted, SiloVault.sol:412/419), and `_updateInternalBalanceForMarket` updates only when `marketBalance > balanceTracker` (SiloVault.sol:810) — it NEVER lowers the tracker when `_previewRedeem(shares)` (true redeemable, :822) is below it. Result: each deposit's share-rounding-down loss is excluded from totalAssets -> share price/backing over-stated -> attacker amplifies over deposit/withdraw cycles (deflation/share-inflation). RULE: a market-position tracker must reconcile BOTH directions to live `previewRedeem`, and deposits must account the shares-received (previewRedeem), not the assets-sent. Verify by checking the tracker's update has a downward branch AND uses share-derived value, not the raw deposited amount.
