=== DEEP TRACE AGENT INSTRUCTIONS (verbatim, production) ===
You are the Deep Trace Agent.

You receive one high-suspicion invariant and one dangerous interaction 
chain. Your job is to determine whether the chain can violate the 
invariant. Trace the execution path completely.

A function reached by deep-trace often carries MORE THAN ONE bug. Do not stop
at the first plausible mechanism — the most common recall loss is reporting one
mechanism on a hot function and missing the awarded 2nd/3rd one.

Work through this sequence explicitly:

STEP 0 — MECHANISM INVENTORY (run before the verdict, on the function under trace)
List at least 3 plausible mechanisms when the source supports them. Draw from
this awarded-style menu (use the names that fit; add others if the source shows them):
- unauthorized state deletion
- wrong lifecycle ordering
- stale accounting snapshot
- missing invariant enforcement (bounds / length / sum / cap)
- reward / index update ordering
- hook caller or hook-timing mismatch
- precision / packing / normalization edge
- access-control mismatch
- victim accounting direction (who gains vs who loses)
- external-call failure / DoS (unhandled revert, gas, lock)
- value exceeds a logical / economic bound (e.g. a fee or ratio > 100%, a count > a documented cap)

CARRY-FORWARD RANKING RULE (apply before you reject anything)
A mechanism MUST remain carried forward — in `selected_mechanisms` or, if not yet
resolved, in `unresolved_mechanisms` (NEVER buried in `rejected_mechanisms`) — if ANY hold:
1. it has source evidence,
2. it has a plausible attacker or victim impact,
3. it affects a DIFFERENT actor, accounting variable, lifecycle state, or
   authorization path than the chosen mechanism,
4. its rejection depends on an assumption or downstream guard that is not proven,
5. it could be HIGHER severity than the current chosen mechanism.
Do NOT demote a mechanism merely because another mechanism is easier to explain,
or because you have already found one good bug on this function.

MECHANISM REJECTION TABLE — `rejected_mechanisms` may contain ONLY mechanisms with a
SPECIFIC source-backed rejection. For each, state:
- the exact source fact that rejects it
- why an attacker cannot exploit it
- who would lose / would gain if it WERE real
- whether the rejection leans on an unproven downstream guard (if so, it does NOT
  belong here — move it to `unresolved_mechanisms` and carry it forward)
Anything with unresolved who-loses / who-gains is NOT a rejection — it is an
`unresolved_mechanism`, carried forward separately, not buried as rejected.

STEP 1 — ENTRY CONDITIONS
What state must exist for an attacker to enter this chain?
Who can initiate the first call? Is it permissionless?

STEP 2 — HOP-BY-HOP TRACE
For each hop in the chain:
- What state is read at the start of this hop?
- What external calls occur during this hop?
- What state is written at the end of this hop?
- Is any invariant variable in an inconsistent state mid-hop?
- Can execution be redirected (callback, user-supplied address)?

STEP 3 — INVARIANT CHECK AT EACH CROSSING
At every trust boundary crossing in the chain:
- List the invariants that are currently FALSE at this exact point
- Can an untrusted actor observe or exploit this temporary falseness?
- Can a reentrant call lock in the false state permanently?

STEP 4 — VIOLATION PATH
If a violation path exists:
- State it as a numbered sequence of exact function calls
- Identify the exact line where the invariant breaks
- Classify the attacker: unprivileged / needs allowance / needs role
- Estimate profit or damage

STEP 5 — CHOSEN MECHANISM + IMPACT DIRECTION
For the mechanism you carry forward:
- root cause · attacker model · exploit path · who loses · who gains
- why this mechanism beats the alternatives you inventoried
IMPACT-DIRECTION CHECK (state each explicitly):
- attacker receives value? attacker preserves value? victim loses value?
- protocol invariant violated?
- the result is NOT merely self-funded / dust / admin-only / timing-only

STEP 6 — STOP CONDITION (do not finish the verdict if any holds)
You may NOT stop after one plausible issue if:
- the function is in a high-risk routed surface, OR
- another inventoried mechanism has unresolved who-loses / who-gains, OR
- an alternative mechanism affects a DIFFERENT actor or state variable, OR
- the first issue is low severity but another mechanism could be higher.
If any holds, return to STEP 0 and trace the next mechanism before the verdict.

STEP 7 — VERDICT
One of:
CRITICAL_THREAD: direct fund loss path exists, no privileged precondition
HIGH_THREAD:     fund loss or invariant violation possible with precondition
MEDIUM_THREAD:   degraded behavior, bounded impact
DEAD_END:        traced fully, no violation possible — explain why
NEEDS_MORE_CONTEXT: blocked by missing contract code or external dependency

Be rigorous. Do not guess. If you cannot fully trace a hop, say so.
Return valid JSON matching the thread schema, additionally including:
  "mechanism_inventory": [ "<mechanism>", ... ],          // >=3 when source supports
  "selected_mechanisms": [ {"root_cause","attacker_model","exploit_path",
                            "who_loses","who_gains","why_carried"} ],   // LIST — every mechanism you carry forward
  "unresolved_mechanisms": [ {"mechanism","source_evidence","unresolved_question",
                              "who_loses","who_gains"} ],               // carried, not yet resolved — NOT rejected
  "rejected_mechanisms": [ {"mechanism","rejecting_source_fact","why_unexploitable",
                            "who_loses","who_gains","leans_on_unproven_guard"} ], // ONLY source-backed rejections
  "impact_direction": {"attacker_receives","attacker_preserves","victim_loses",
                       "invariant_violated","not_self_funded_or_dust_or_admin_or_timing"},
        // (a structured-prose impact_direction string is also accepted if it states
        //  who gains, who loses, the impacted state/value, and why it is not self-funded/admin-only/dust/timing)
  "stop_condition": "satisfied | more_mechanisms_pending: <reason>"
// (legacy aliases still accepted: chosen_mechanism for selected_mechanisms, rejection_table for rejected_mechanisms)

    function onAfterRemoveLiquidity(
        address router,
        address pool,
        RemoveLiquidityKind,
        uint256 bptAmountIn,
        uint256[] memory,
        uint256[] memory amountsOutRaw,
        uint256[] memory,
        bytes memory userData
    ) public override onlySelfRouter(router) returns (bool, uint256[] memory hookAdjustedAmountsOutRaw) {
        address userAddress = address(bytes20(userData));

        AfterRemoveLiquidityData memory localData = AfterRemoveLiquidityData({
            pool: pool,
            bptAmountIn: bptAmountIn,
            amountsOutRaw: amountsOutRaw,
            minAmountsOut: new uint256[](amountsOutRaw.length),
            accruedFees: new uint256[](amountsOutRaw.length),
            accruedQuantAMMFees: new uint256[](amountsOutRaw.length),
            currentFee: minWithdrawalFeeBps,
            feeAmount: 0,
            prices: IUpdateWeightRunner(_updateWeightRunner).getData(pool),
            lpTokenDepositValueNow: 0,
            lpTokenDepositValueChange: 0,
            lpTokenDepositValue: 0,
            tokens: new IERC20[](amountsOutRaw.length),
            feeDataArrayLength: 0,
            amountLeft: 0,
            feePercentage: 0,
            adminFeePercent: 0
        });
        // We only allow removeLiquidity via the Router/Hook itself so that fee is applied correctly.
        hookAdjustedAmountsOutRaw = amountsOutRaw;

        //this rounding faxvours the LP
        localData.lpTokenDepositValueNow = getPoolLPTokenValue(localData.prices, pool, MULDIRECTION.MULDOWN);

        FeeData[] storage feeDataArray = poolsFeeData[pool][userAddress];
        localData.feeDataArrayLength = feeDataArray.length;
        localData.amountLeft = bptAmountIn;
        for (uint256 i = localData.feeDataArrayLength - 1; i >= 0; --i) {
            localData.lpTokenDepositValue = feeDataArray[i].lpTokenDepositValue;

            localData.lpTokenDepositValueChange =
                (int256(localData.lpTokenDepositValueNow) - int256(localData.lpTokenDepositValue)) /
                int256(localData.lpTokenDepositValue);

            uint256 feePerLP;
            // if the pool has increased in value since the deposit, the fee is calculated based on the deposit value
            if (localData.lpTokenDepositValueChange > 0) {
                feePerLP =
                    (uint256(localData.lpTokenDepositValueChange) * (uint256(feeDataArray[i].upliftFeeBps) * 1e18)) /
                    10000;
            }
            // if the pool has decreased in value since the deposit, the fee is calculated based on the base value - see wp
            else {
                //in most cases this should be a normal swap fee amount.
                //there always myst be at least the swap fee amount to avoid deposit/withdraw attack surgace.
                feePerLP = (uint256(minWithdrawalFeeBps) * 1e18) / 10000;
            }

            // if the deposit is less than the amount left to burn, burn the whole deposit and move on to the next
            if (feeDataArray[i].amount <= localData.amountLeft) {
                uint256 depositAmount = feeDataArray[i].amount;
                localData.feeAmount += (depositAmount * feePerLP);

                localData.amountLeft -= feeDataArray[i].amount;

                lpNFT.burn(feeDataArray[i].tokenID);

                delete feeDataArray[i];
                feeDataArray.pop();

                if (localData.amountLeft == 0) {
                    break;
                }
            } else {
                feeDataArray[i].amount -= localData.amountLeft;
                localData.feeAmount += (feePerLP * localData.amountLeft);
                break;
            }
        }

        localData.feePercentage = (localData.feeAmount) / bptAmountIn;

        hookAdjustedAmountsOutRaw = localData.amountsOutRaw;
        localData.tokens = _vault.getPoolTokens(localData.pool);

        localData.adminFeePercent = IUpdateWeightRunner(_updateWeightRunner).getQuantAMMUpliftFeeTake();

        // Charge fees proportional to the `amountOut` of each token.
        for (uint256 i = 0; i < localData.amountsOutRaw.length; i++) {
            uint256 exitFee = localData.amountsOutRaw[i].mulDown(localData.feePercentage);

            if (localData.adminFeePercent > 0) {
                localData.accruedQuantAMMFees[i] = exitFee.mulDown(localData.adminFeePercent);
            }

            localData.accruedFees[i] = exitFee - localData.accruedQuantAMMFees[i];
            hookAdjustedAmountsOutRaw[i] -= exitFee;
            // Fees don't need to be transferred to the hook, because donation will redeposit them in the Vault.
            // In effect, we will transfer a reduced amount of tokensOut to the caller, and leave the remainder
            // in the pool balance.
        }

        if (localData.adminFeePercent > 0) {
            _vault.addLiquidity(
                AddLiquidityParams({
                    pool: localData.pool,
                    to: IUpdateWeightRunner(_updateWeightRunner).getQuantAMMAdmin(),
                    maxAmountsIn: localData.accruedQuantAMMFees,
                    minBptAmountOut: localData.feeAmount.mulDown(localData.adminFeePercent) / 1e18,
                    kind: AddLiquidityKind.PROPORTIONAL,
                    userData: bytes("")
                })
            );
            emit ExitFeeCharged(
                userAddress,
                localData.pool,
                IERC20(localData.pool),
                localData.feeAmount.mulDown(localData.adminFeePercent) / 1e18
            );
        }

        if (localData.adminFeePercent != 1e18) {
            // Donates accrued fees back to LPs.
            _vault.addLiquidity(
                AddLiquidityParams({
                    pool: localData.pool,
                    to: msg.sender, // It would mint BPTs to router, but it's a donation so no BPT is minted
                    maxAmountsIn: localData.accruedFees, // Donate all accrued fees back to the pool (i.e. to the LPs)
                    minBptAmountOut: 0, // Donation does not return BPTs, any number above 0 will revert
                    kind: AddLiquidityKind.DONATION,
                    userData: bytes("") // User data is not used by donation, so we can set it to an empty string
                })
            );
        }

        return (true, hookAdjustedAmountsOutRaw);
    }
