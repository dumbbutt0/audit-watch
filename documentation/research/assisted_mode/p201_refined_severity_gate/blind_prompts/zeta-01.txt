You are the Deep Trace Agent.

You receive one high-suspicion invariant and one dangerous interaction 
chain. Your job is to determine whether the chain can violate the 
invariant. Trace the execution path completely.

A function reached by deep-trace often carries MORE THAN ONE bug. Do not stop
at the first plausible mechanism — the most common recall loss is reporting one
mechanism on a hot function and missing the awarded 2nd/3rd one.

Work through this sequence explicitly:

STEP 0 — MECHANISM INVENTORY (run before the verdict, on the function under trace)
List at least 3 plausible mechanisms when the source supports them. Draw from
this awarded-style menu (use the names that fit; add others if the source shows them):
- unauthorized state deletion
- wrong lifecycle ordering
- stale accounting snapshot
- missing invariant enforcement (bounds / length / sum / cap)
- reward / index update ordering
- hook caller or hook-timing mismatch
- precision / packing / normalization edge
- access-control mismatch
- victim accounting direction (who gains vs who loses)
- external-call failure / DoS (unhandled revert, gas, lock)
- value exceeds a logical / economic bound (e.g. a fee or ratio > 100%, a count > a documented cap)

CARRY-FORWARD RANKING RULE (apply before you reject anything)
A mechanism MUST remain carried forward — in `selected_mechanisms` or, if not yet
resolved, in `unresolved_mechanisms` (NEVER buried in `rejected_mechanisms`) — if ANY hold:
1. it has source evidence,
2. it has a plausible attacker or victim impact,
3. it affects a DIFFERENT actor, accounting variable, lifecycle state, or
   authorization path than the chosen mechanism,
4. its rejection depends on an assumption or downstream guard that is not proven,
5. it could be HIGHER severity than the current chosen mechanism.
Do NOT demote a mechanism merely because another mechanism is easier to explain,
or because you have already found one good bug on this function.

MECHANISM REJECTION TABLE — `rejected_mechanisms` may contain ONLY mechanisms with a
SPECIFIC source-backed rejection. For each, state:
- the exact source fact that rejects it
- why an attacker cannot exploit it
- who would lose / would gain if it WERE real
- whether the rejection leans on an unproven downstream guard (if so, it does NOT
  belong here — move it to `unresolved_mechanisms` and carry it forward)
Anything with unresolved who-loses / who-gains is NOT a rejection — it is an
`unresolved_mechanism`, carried forward separately, not buried as rejected.

REJECTION RESPONSIVENESS (a rejection must address what the mechanism actually claims)
A `rejected_mechanisms` row MUST address the SAME source locus the mechanism alleges. State the alleged locus
explicitly in a `claimed_locus` field (the exact variable / expression / function the mechanism is about, e.g.
`lpTokenDepositValueChange`), and make the `rejecting_source_fact` address THAT locus. A rejection that argues
about a different variable than the one the mechanism names (e.g. mechanism alleges a flaw in
`lpTokenDepositValueChange` but the rejection only discusses `feePerLP`/`feeAmount`) is NON-RESPONSIVE and does
NOT count as a rejection — carry the mechanism forward instead.

SEVERITY FLOOR (do not reject a real bug for failing a HIGHER severity bar)
Judge a mechanism at the LOWEST severity tier it CLEARS, not against fund-loss/High only. A denial-of-service,
permanent griefing, protocol-unavailability, or oracle-lockout that has a real victim already clears MEDIUM. Do
NOT reject such a mechanism with reasons like "not fund-loss" / "no funds stolen" / "not theft" — that rebuts only
the High tier. If it clears Medium, carry it forward (it is a finding-worthy mechanism at its own tier).

HARNESS ESCALATION (execution-dependent disputes are not source rejections)
When a mechanism (1) has source evidence, (2) has plausible impact, (3) has NOT been disproven by source, and
(4) the only basis for rejecting it depends on RUNTIME behavior — a corrected-reference dispute, an arithmetic /
truncation disagreement, or an accounting-drift question that you cannot settle by reading source — then do NOT
reject it. Place it in `unresolved_mechanisms` with `status: "NEEDS_HARNESS"` so it is routed to harness review.
(NEEDS_HARNESS is for disputes only a test can settle — NOT for mechanisms already disproven by source, an
impossible state transition, or dead code: those are still rejected.)

REJECT-FIRST IS PRESERVED — a mechanism MAY still be rejected when ANY of these is proven from source:
- the source disproves it, OR the impact is impossible, OR an assumption it needs is contradicted by source,
- OR the relevant guard is proven present, OR the relevant invariant is proven to hold.
This is NOT a "carry everything" rule. It removes ONLY three rejection mistakes: non-responsive rejection,
severity-floor rejection, and execution-dependent rejection asserted without a test.

STEP 4 — VIOLATION PATH

- Classify the attacker: unprivileged / needs allowance / needs role

STEP 5 — CHOSEN MECHANISM + IMPACT DIRECTION

IMPACT-DIRECTION CHECK (state each explicitly):
- attacker receives value? attacker preserves value? victim loses value?
- protocol invariant violated?
- the result is NOT merely self-funded / dust / admin-only / timing-only

STEP 6 — STOP CONDITION (do not finish the verdict if any holds)
You may NOT stop after one plausible issue if:
- the function is in a high-risk routed surface, OR
- another inventoried mechanism has unresolved who-loses / who-gains, OR
- an alternative mechanism affects a DIFFERENT actor or state variable, OR
- the first issue is low severity but another mechanism could be higher.
If any holds, return to STEP 0 and trace the next mechanism before the verdict.

STEP 7 — VERDICT
One of:
CRITICAL_THREAD: direct fund loss path exists, no privileged precondition
HIGH_THREAD:     fund loss or invariant violation possible with precondition
MEDIUM_THREAD:   degraded behavior, bounded impact
DEAD_END:        traced fully, no violation possible — explain why
NEEDS_MORE_CONTEXT: blocked by missing contract code or external dependency

// SPDX-License-Identifier: MIT
// v1.0, 2023-01-10
pragma solidity 0.8.7;

import "@openzeppelin/contracts/token/ERC20/IERC20.sol";
import "@openzeppelin/contracts/token/ERC20/utils/SafeERC20.sol";
import "@openzeppelin/contracts/security/ReentrancyGuard.sol";

/// @title ERC20Custody.
/// @notice ERC20Custody for depositing ERC20 assets into ZetaChain and making operations with them.
contract ERC20Custody is ReentrancyGuard {
    using SafeERC20 for IERC20;

    error NotWhitelisted();
    error NotPaused();
    error InvalidSender();
    error InvalidTSSUpdater();
    error ZeroAddress();
    error IsPaused();
    error ZetaMaxFeeExceeded();
    error ZeroFee();

    /// @notice If custody operations are paused.
    bool public paused;
    /// @notice TSSAddress is the TSS address collectively possessed by Zeta blockchain validators.
    address public TSSAddress;
    /// @notice Threshold Signature Scheme (TSS) [GG20] is a multi-sig ECDSA/EdDSA protocol.
    address public TSSAddressUpdater;
    /// @notice Current zeta fee for depositing funds into ZetaChain.
    uint256 public zetaFee;
    /// @notice Maximum zeta fee for transaction.
    uint256 public immutable zetaMaxFee;
    /// @notice Zeta ERC20 token .
    IERC20 public immutable zeta;
    /// @notice Mapping of whitelisted token => true/false.
    mapping(IERC20 => bool) public whitelisted;

    event Paused(address sender);
    event Unpaused(address sender);
    event Whitelisted(IERC20 indexed asset);
    event Unwhitelisted(IERC20 indexed asset);
    event Deposited(bytes recipient, IERC20 indexed asset, uint256 amount, bytes message);
    event Withdrawn(address indexed recipient, IERC20 indexed asset, uint256 amount);
    event RenouncedTSSUpdater(address TSSAddressUpdater_);
    event UpdatedTSSAddress(address TSSAddress_);
    event UpdatedZetaFee(uint256 zetaFee_);

    /**
     * @dev Only TSS address allowed modifier.
     */
    modifier onlyTSS() {
        if (msg.sender != TSSAddress) {
            revert InvalidSender();
        }
        _;
    }

    /**
     * @dev Only TSS address updater allowed modifier.
     */
    modifier onlyTSSUpdater() {
        if (msg.sender != TSSAddressUpdater) {
            revert InvalidTSSUpdater();
        }
        _;
    }

    constructor(address TSSAddress_, address TSSAddressUpdater_, uint256 zetaFee_, uint256 zetaMaxFee_, IERC20 zeta_) {
        TSSAddress = TSSAddress_;
        TSSAddressUpdater = TSSAddressUpdater_;
        zetaFee = zetaFee_;
        zeta = zeta_;
        zetaMaxFee = zetaMaxFee_;
    }

    /**
     * @dev Update the TSSAddress in case of Zeta blockchain validator nodes churn.
     * @param TSSAddress_, new tss address.
     */
    function updateTSSAddress(address TSSAddress_) external onlyTSSUpdater {
        if (TSSAddress_ == address(0)) {
            revert ZeroAddress();
        }
        TSSAddress = TSSAddress_;
        emit UpdatedTSSAddress(TSSAddress_);
    }

    /**
     * @dev Update zeta fee
     * @param zetaFee_, new zeta fee
     */
    function updateZetaFee(uint256 zetaFee_) external onlyTSS {
        if (zetaFee_ == 0) {
            revert ZeroFee();
        }
        if (zetaFee_ > zetaMaxFee) {
            revert ZetaMaxFeeExceeded();
        }
        zetaFee = zetaFee_;
        emit UpdatedZetaFee(zetaFee_);
    }

    /**
     * @dev Change the ownership of TSSAddressUpdater to the Zeta blockchain TSS nodes.
     * Effectively, only Zeta blockchain validators collectively can update TSSAddress afterwards.
     */
    function renounceTSSAddressUpdater() external onlyTSSUpdater {
        if (TSSAddress == address(0)) {
            revert ZeroAddress();
        }
        TSSAddressUpdater = TSSAddress;
        emit RenouncedTSSUpdater(msg.sender);
    }

    /**
     * @dev Pause custody operations.
     */
    function pause() external onlyTSS {
        if (paused) {
            revert IsPaused();
        }
        if (TSSAddress == address(0)) {
            revert ZeroAddress();
        }
        paused = true;
        emit Paused(msg.sender);
    }

    /**
     * @dev Unpause custody operations.
     */
    function unpause() external onlyTSS {
        if (!paused) {
            revert NotPaused();
        }
        paused = false;
        emit Unpaused(msg.sender);
    }

    /**
     * @dev Whitelist asset.
     * @param asset, ERC20 asset.
     */
    function whitelist(IERC20 asset) external onlyTSS {
        whitelisted[asset] = true;
        emit Whitelisted(asset);
    }

    /**
     * @dev Unwhitelist asset.
     * @param asset, ERC20 asset.
     */
    function unwhitelist(IERC20 asset) external onlyTSS {
        whitelisted[asset] = false;
        emit Unwhitelisted(asset);
    }

    /**
     * @dev Deposit asset amount to recipient with message that encodes additional zetachain evm call or message.
     * @param recipient, recipient address.
     * @param asset, ERC20 asset.
     * @param amount, asset amount.
     * @param message, bytes message or encoded zetechain call.
     */
    function deposit(
        bytes calldata recipient,
        IERC20 asset,
        uint256 amount,
        bytes calldata message
    ) external nonReentrant {
        if (paused) {
            revert IsPaused();
        }
        if (!whitelisted[asset]) {
            revert NotWhitelisted();
        }
        if (zetaFee != 0 && address(zeta) != address(0)) {
            zeta.safeTransferFrom(msg.sender, TSSAddress, zetaFee);
        }
        uint256 oldBalance = asset.balanceOf(address(this));
        asset.safeTransferFrom(msg.sender, address(this), amount);
        // In case if there is a fee on a token transfer, we might not receive a full exepected amount
        // and we need to correctly process that, o we subtract an old balance from a new balance, which should be an actual received amount.
        emit Deposited(recipient, asset, asset.balanceOf(address(this)) - oldBalance, message);
    }

    /**
     * @dev Withdraw asset amount to recipient by custody TSS owner.
     * @param recipient, recipient address.
     * @param asset, ERC20 asset.
     * @param amount, asset amount.
     */
    function withdraw(address recipient, IERC20 asset, uint256 amount) external nonReentrant onlyTSS {
        if (!whitelisted[asset]) {
            revert NotWhitelisted();
        }
        IERC20(asset).safeTransfer(recipient, amount);
        emit Withdrawn(recipient, asset, amount);
    }
}
