# POS-001 — Leverage ladder is enforced per-position, not per-account: notional-based leverage cap is bypassable by splitting exposure across positions / sub-accounts

- **Severity (recommended):** Medium
- **Category (HackenProof VRT):** Business Logic Errors
- **Confidence:** High
- **ICE:** Impact=aggregate under-collateralised exposure beyond the ladder's design target -> elevated protocol bad-debt / cascading-liquidation risk under adverse moves · Confidence=- · Exploitability=-
- **Location(s):** `contracts/position/LeverageLadderUtils.sol:26-50; contracts/position/PositionUtils.sol:519-535 (willPositionCollateralBeSufficient)`
- **Vulnerable files (bundled in `sources/`):** `Position.sol`, `MarketUtils.sol`, `LeverageLadderUtils.sol`, `PositionUtils.sol`

## Description

The leverage ladder is the protocol's headline custom risk control: LeverageLadderUtils.getMaxLeverageForNotional() walks ascending notional tiers and returns the max leverage of the first tier whose maxNotionalUsd >= the POST-TRADE notional, so larger positions get tighter leverage (e.g. configured 0-50k -> 50x, 50k-200k -> 25x, 200k+ -> 10x). PositionUtils.willPositionCollateralBeSufficient (line 519-526) consumes this as one of the three collateral floors (tightest-of max_leverage / OI-multiplier / ladder, lines 528-535), requiring collateral >= sizeInUsd / ladderMaxLeverage where the ladder tier is selected from values.positionSizeInUsd. The selection math (decimalToFloat-scaled leverages, '<=' boundary semantics, strictly-ascending notionals, non-increasing leverages, type(uint256).max catch-all tail, stale-row clear) is all implemented correctly and matches the intended-behaviour tests (test/position/LeverageLadder.integration.ts, test/exchange/DynamicMmr.ts). The flaw is structural, not arithmetic: the ladder tier is chosen from the size of ONE position only. Positions are keyed keccak256(account, market, collateralToken, isLong) (Position.sol:200-203), and there is NO per-account aggregate-notional or position-count cap anywhere in the open/increase flow (confirmed by grep across position/order/exchange). A trader wanting $1M of exposure that the ladder intends to cap at 10x can instead open ~20 separate $50k positions (different sub-account EOAs, or different collateral tokens / direction keys) each falling in the lowest tier -> each is allowed 50x. The notional-based concentration tapering the ladder exists to enforce is therefore defeated permissionlessly at gas cost only. The aggregate-aware OI floor (getMinCollateralFactorForOpenInterest, MarketUtils.sol:2026-2036) only mitigates this when minCollateralFactorForOpenInterestMultiplier is configured > 0; with the common 0 default the only surviving per-position floor is the market-wide max_leverage (e.g. 100x), and aggregate exposure at small-tier leverage is unbounded by the ladder.

## Impact

The protocol's intended notional-based leverage cap (added to limit concentration / insolvency risk from very large positions) does not constrain a determined trader's aggregate position. A whale can run aggregate exposure at the high small-tier leverage, exactly the scenario the ladder was built to prevent, increasing protocol bad-debt / cascading-liquidation risk under an adverse price move. No direct theft and no single position exceeds the market max_leverage, so this is a risk-management-control bypass rather than a fund-loss bug.

## Attack path (Intent / Technique / Evasion)

- **Intent:** A whale obtains the lowest-tier (highest) leverage on an aggregate notional that the ladder intends to force into a higher, lower-leverage tier, defeating the protocol's concentration control and raising its insolvency exposure.
- **Technique:** Instead of one large position (post-trade notional lands in a high tier -> low ladder leverage -> high collateral floor in willPositionCollateralBeSufficient), open N small positions each below the first tier boundary, using N sub-account EOAs (or distinct collateralToken/isLong position keys per Position.getPositionKey). Each getMaxLeverageForNotional call sees only that position's size, returns the small-tier leverage, and willPositionCollateralBeSufficient only requires size/smallTierLeverage collateral. Aggregate exposure = N x smallSize at smallTierLeverage.
- **Evasion:** The developer intended getMaxLeverageForNotional(notionalUsd=positionSizeInUsd) to taper leverage by size, but the floor is evaluated against a single position's size and positions are independently keyed with no account-level aggregation, so the cap that should bind aggregate exposure binds only one slice of it.
